先查环境和索引，再测数据库、完整接口和页面。所有大规模造数与压测均使用专用测试环境。

## A 四阶段顺序
```flow LR
环境与索引 -> 数据库基线: 条件核对通过
数据库基线 -> 接口并发: 查询结果正确
接口并发 -> 部署与页面: 容量边界已知
```

范围是 secret/search 和 secret/search/tag/list。当前先做方案，不开发值检索或标签统计。

## B 复用现有脚本，但补齐覆盖
已有脚本能生成十万和百万条环境实例，并测量查询与执行计划。四套环境时，百万条实例约为二十五万组 Key。

脚本使用占位密文，未接入真实标签仓储。它不覆盖解密、审计、完整 HTTP 或页面渲染，也没有并发采样。

建议补充多租户、多项目、目录、标签和热点数据。长值只放入专项样例，避免把全库放大。

## C 每个阶段做什么
| 阶段 | 核验内容 | 交付 |
| --- | --- | --- |
| 环境与索引 | PostgreSQL 版本、pg_trgm、GIN 索引有效性、统计信息和连接池 | 环境与索引清单 |
| 数据库基线 | 少量命中、高频词、中文、标签、深分页、执行计划 | SQL 各阶段耗时 |
| 完整接口 | JWT、用户检查、查询、解密、审计、响应传输 | P95、吞吐、错误及资源占用 |
| 部署与页面 | 后端直连、网关与 Web Nginx、表格渲染 | 确定额外耗时来源 |

先检查索引状态，再按变更流程修复缺失项。同名索引存在不代表索引有效。

## D 规模和测试方式
| 项目 | 第一轮安排 |
| --- | --- |
| 数据量 | 一万、十万、百万条环境实例 |
| 每页组数 | 二十、一百、二百 |
| 页码 | 首页与确实有结果的深页 |
| 并发 | 一、五、十、二十逐级增加 |
| 接口采样 | 每级预热三十秒，再测三分钟 |
| 值与环境 | 基础四环境，专项验证多环境与长值 |

记录中位数、P95、吞吐和完成样本数。样本不足时不作稳定 P99 结论。

HTTP 200 不代表成功，还需检查业务 code。参数拒绝、预期取消、超时和未知错误分别计数。

## E 建议指标与完成条件
以下为建议目标，不是已经测得的结果。

| 指标 | 第一轮建议 |
| --- | --- |
| 常规搜索 | 二十组、并发不超过十，完整接口 P95 不超过一秒 |
| 标签候选 | 同一正常负载下 P95 不超过五百毫秒 |
| 高频词与深页 | 低并发 P95 不超过三秒，另报容量边界 |
| 正确性 | 总数、组分页、环境和标签均符合预设结果 |
| 取消与超时 | 查询结束后连接可复用，不返回半页成功数据 |

五秒配置是搜索查询及解密预算，不能当成完整 HTTP 上限。审计与网络开销单独核验。

报告还记录 CPU、内存、数据库等待、响应大小及执行计划。发现瓶颈后再决定是否优化 SQL 或分页。

详细方案位于后端 design/secret-search-performance.md。方案包含只读索引检查 SQL、现有测试命令和实施文件范围。
