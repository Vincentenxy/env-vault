建议近期先完成索引和性能验收，再开发标签统计。权限中心独立推进，值检索先确定规则和代价。

## A 为什么这样排序
```flow LR
核验现有搜索 -> 标签分类统计: 明确统计成本
标签分类统计 -> 值检索设计: 先确认业务需求
值检索设计 -> 受限值检索: 规则确认后开发
```

性能验收不一定需要改代码。若索引、查询耗时与并发已达标，直接进入标签统计。

权限接入是独立工作。权限中心就绪后，应优先覆盖全部搜索查询，不能只隐藏前端选项。

## B 第一阶段：核验现有搜索
- 检查目标数据库的 pg_trgm 和两个 GIN 索引
- 验证少量命中、高频词、中文短词和深分页
- 分别测量计数、分页、详情、标签和解密耗时
- 验证大值、多环境和并发下的响应大小与超时

验收后再决定是否优化 SQL、精确计数或分页。历史百万行样例不是生产性能保证。

## C 第二阶段：标签分类统计
在标签候选中显示密钥组数量，例如“数据库（db） · 128 组”。继续复用当前页面，不增加独立统计页面。

建议统计规则：
- 按 groupId 去重，不能按环境实例计数
- 应用范围、环境、关键词和将来的权限条件
- 统计候选时不应用已选标签条件，便于追加其他标签
- 多标签仍为任意匹配，各标签数量不能直接相加
- 标签统计与主搜索使用同一套查询条件构造能力

先按需返回候选标签的数量，避免每次搜索聚合全部标签。统计时不读取或解密密钥值。

## D 第三阶段：值检索先设计
值以密文存储，当前 Key 和备注的索引不能用于值匹配。

需要先确认：
- 业务需要精确匹配还是包含匹配
- 是否仅限指定项目或文件夹
- allowValueSearch 如何参与筛选，多标签冲突如何处理
- 单次允许检查的数据量、超时和取消行为
- 结果分页、命中总数和匹配环境如何定义

若需要包含匹配，可先评估范围受限的候选解密方案。候选仍可能很多，不能默认全库解密扫描。

不能只解密元数据的当前页再匹配。这样会漏掉其他页的值命中，total 也不准确。

推荐先做后端受限查询与正确性测试，再增加页面的搜索字段选择。是否实施取决于设计和性能结果。

## E 其他事项何时做
| 事项 | 建议时机 |
| --- | --- |
| 资源和环境权限 | 权限中心可用后优先接入，并覆盖统计和标签候选 |
| 共用历史组件 | 修改历史交互或重复维护明显时整理 |
| 单环境标签 | 业务确认跨环境标签不能满足需求时再设计 |
| 全量导出 | 有明确导出需求后独立开发 |
| 游标分页或搜索引擎 | 性能验收发现具体瓶颈后选择 |

近期开发建议选标签统计。近期上线工作建议先核验索引和实际查询性能。
