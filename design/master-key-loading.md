# 主密钥分片加载设计

> 状态：方案已确认，按阶段实施
>
> 本文档记录主密钥加载方案、实施顺序和阶段验收范围

## 1. 目标

- 将当前 `security.encryption_key` 改为优先从外部 Shamir 分片恢复
- 主密钥拆分为 5 份，任意 3 份可重组 AES-256-GCM 主密钥
- 外部主密钥未加载时，开发环境可回退到 `config.yaml`
- 系统在主密钥未就绪时仍能启动 HTTP 服务
- 主密钥正确加载后，系统自动切换为可服务状态
- 未就绪时拦截普通接口，但放行配置指定的启动相关接口

## 2. 建议结构

新增并发安全的主密钥模块，统一负责：

- 整批接收并校验用于本次恢复的三个分片
- 达到阈值后重组主密钥
- 校验主密钥是否正确
- 激活 AES-256-GCM 加解密器
- 提供 `Ready()`、`Encrypt()`、`Decrypt()` 能力
- 主密钥未激活时，加解密返回“密钥未就绪”错误

Secret 服务和新增环境复制逻辑统一依赖该模块，不再直接持有启动时创建的 Cipher。

系统是否可提供服务直接使用主密钥模块的 `Ready()` 状态，不单独维护第二份布尔状态，避免状态不一致。

## 3. 启动流程

1. 创建未激活的主密钥模块
2. 开发环境根据配置开关尝试读取 `security.encryption_key`
3. 未通过配置激活时等待管理员一次提交任意 3 份 Shamir 分片
4. 校验分片格式、批次、编号和完整性后重组主密钥
5. 主密钥正确时设置为 Ready
6. 主密钥未就绪时仍启动 HTTP 服务，等待后续输入分片
7. 后续分片满足条件后原子切换为 Ready，无需重启 Router

## 4. 请求拦截

Ready 中间件挂载在全局 Router，位于业务路由之前。

- `Ready=true`：正常放行
- `Ready=false`：白名单接口放行，其他接口终止请求
- 未就绪响应使用 HTTP 200：

```json
{
  "code": -2,
  "msg": "系统启动中",
  "data": null
}
```

白名单建议按 HTTP Method 和精确 Path 配置，首批至少考虑：

- 健康检查
- 主密钥状态查询
- 分片提交接口

## 5. 安全约束

- 禁止在日志、错误响应和监控指标中输出分片或完整主密钥
- 分片仅保存在进程内存，不写入数据库或 Redis
- 主密钥切换必须并发安全
- 主密钥激活前不得执行 Secret 加解密
- 分片提交接口本阶段允许未认证访问，后续接入独立的访问保护
- 在线密钥轮换不纳入本次范围，除非另行确认

首次初始化时，三份合法且同批次的分片恢复出的密钥即为系统主密钥，不通过解密数据库 Secret 做额外校验。后续从旧 Pod 获取主密钥时，再设计 Pod 身份认证、传输保护和密钥指纹校验。

## 8. 已确认实施顺序

### 第一阶段：主密钥模块骨架（已完成）

- 创建 `internal/masterkey` 独立模块
- 定义并发安全的 `Manager`、状态、错误和加解密接口
- 实现未就绪保护、单次激活和激活后的加解密能力
- 本阶段不接入配置、Router 和现有 Secret 业务

### 第二阶段：动态加解密接入（已完成）

- Secret 服务和环境资源复制逻辑改为依赖加解密接口
- Router 不再要求启动时必须创建固定 `Cipher`
- 主密钥未就绪时服务仍能完成 HTTP 启动

### 第三阶段：开发环境配置回退（已完成）

- 在 `SecurityConfig` 增加明确的配置回退开关
- 开关启用且配置密钥有效时自动激活主密钥
- 不根据环境名称进行隐式判断

### 第四阶段：Shamir 分片恢复（已完成）

- 实现 3-of-5 分片恢复，任意 3 份且不要求输入顺序
- 校验分片批次、编号、重复项、格式和完整性
- 三份分片整批提交并原子恢复，失败时不保留部分分片
- 本阶段不提供分片生成接口和页面

分片 Token 固定使用 `EVS1.<Base64URL(JSON)>` 格式，JSON 内容包含：

- `keySetId`：本次分片生成批次的 UUID，每次重新生成必须使用新的值
- `index`：Shamir 原始分片中的唯一编号
- `data`：Base64 编码的 33 字节原始分片
- `checksum`：Token 版本和上述字段的 SHA-256 校验值

SHA-256 校验用于发现误输和数据损坏，不用于替代接口认证。本阶段一次提交正好三个 Token，不保留未达到阈值的部分分片。

### 第五阶段：公开接口（已完成）

- 增加 `GET /api/v1/pub/masterKey/status`
- 增加 `POST /api/v1/pub/masterKey/shares`
- 激活后拒绝再次提交分片

状态查询接口：

```http
GET /api/v1/pub/masterKey/status
```

```json
{
  "code": 0,
  "msg": "success",
  "data": {
    "ready": false,
    "source": "",
    "totalShares": 5,
    "requiredShares": 3
  }
}
```

分片提交接口：

```http
POST /api/v1/pub/masterKey/shares
Content-Type: application/json
```

```json
{
  "shares": [
    "EVS1.<share-1>",
    "EVS1.<share-2>",
    "EVS1.<share-3>"
  ]
}
```

提交成功后返回与状态查询相同的结构，其中 `ready=true`、`source=shares`。两个接口均不返回主密钥、分片内容和分片批次 ID。分片提交请求体上限为 16 KiB。

### 第六阶段：系统就绪中间件（已完成）

- 未就绪时使用 HTTP 200 返回 `code=-2` 和 `msg=系统启动中`
- 放行健康检查、主密钥接口、登录接口和配置中的白名单
- 主密钥模块的 `Ready()` 是系统就绪状态的唯一数据源

配置示例：

```yaml
security:
  ready_allowlist:
    - method: GET
      path: /api/v1/pub/health
    - method: GET
      path: /api/v1/pub/masterKey/status
    - method: POST
      path: /api/v1/pub/masterKey/shares
    - method: POST
      path: /api/v1/pub/auth/login
```

白名单在 Router 启动时完成规范化和校验，匹配规则为 HTTP Method 加精确 Path，查询参数不参与匹配。状态查询和分片提交接口是完成系统启动的必要路径，配置缺失时 Router 启动失败。Ready 中间件位于具体路由和 JWT 认证之前，未就绪的普通接口不会进入认证和业务 Handler。

### 第七阶段：分片输入前端（已完成）

- 在 `env-vault-web` 增加公开的分片输入页面
- 一次输入并提交三份分片
- 查询主密钥状态并处理激活后的页面跳转
- 处理普通接口返回 `code=-2` 时的页面跳转

前端公开页面路径为 `/masterKey`。页面先查询主密钥状态，只有明确返回 `ready=false` 后才开放三份分片输入；恢复成功后返回触发启动拦截前的站内地址。分片仅保存在页面局部状态，提交成功或页面卸载时清空引用。
