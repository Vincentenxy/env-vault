# 主密钥分片加载设计

> 状态：方案已确认，按阶段实施
>
> 本文档记录主密钥加载方案、实施顺序和阶段验收范围

## 1. 目标

- 将当前 `security.encryption_key` 改为优先从外部 Shamir 分片恢复
- 主密钥拆分为 5 份，任意 3 份可重组 AES-256-GCM 主密钥
- 外部主密钥未加载时，开发环境可回退到 `config.yaml`
- 系统在主密钥未就绪时仍能启动 HTTP 服务
- 主密钥正确加载后，系统自动切换为可服务状态
- 未就绪时拦截普通接口，但放行配置指定的启动相关接口

## 2. 建议结构

新增并发安全的主密钥模块，统一负责：

- 整批接收并校验用于本次恢复的三个分片
- 达到阈值后重组主密钥
- 校验主密钥是否正确
- 激活 AES-256-GCM 加解密器
- 提供 `Ready()`、`Encrypt()`、`Decrypt()` 能力
- 主密钥未激活时，加解密返回“密钥未就绪”错误

Secret 服务和新增环境复制逻辑统一依赖该模块，不再直接持有启动时创建的 Cipher。

系统是否可提供服务直接使用主密钥模块的 `Ready()` 状态，不单独维护第二份布尔状态，避免状态不一致。

## 3. 启动流程

1. 创建未激活的主密钥模块
2. 开发环境根据配置开关尝试读取 `security.encryption_key`
3. 未通过配置激活时等待管理员一次提交任意 3 份 Shamir 分片
4. 校验分片格式、批次、编号和完整性后重组主密钥
5. 主密钥正确时设置为 Ready
6. 主密钥未就绪时仍启动 HTTP 服务，等待后续输入分片
7. 后续分片满足条件后原子切换为 Ready，无需重启 Router

## 4. 请求拦截

Ready 中间件挂载在全局 Router，位于业务路由之前。

- `Ready=true`：正常放行
- `Ready=false`：白名单接口放行，其他接口终止请求
- 未就绪响应使用 HTTP 200：

```json
{
  "code": -2,
  "msg": "系统启动中",
  "data": null
}
```

白名单建议按 HTTP Method 和精确 Path 配置，首批至少考虑：

- 健康检查
- 主密钥状态查询
- 分片提交接口

## 5. 安全约束

- 禁止在日志、错误响应和监控指标中输出分片或完整主密钥
- 分片仅保存在进程内存，不写入数据库或 Redis
- 主密钥切换必须并发安全
- 主密钥激活前不得执行 Secret 加解密
- 分片提交接口本阶段允许未认证访问，后续接入独立的访问保护
- 在线密钥轮换不纳入本次范围，除非另行确认

首次初始化时，三份合法且同批次的分片恢复出的密钥即为系统主密钥，不通过解密数据库 Secret 做额外校验。后续从旧 Pod 获取主密钥时，再设计 Pod 身份认证、传输保护和密钥指纹校验。

### 第二阶段：动态加解密接入（已完成）

- Secret 服务和环境资源复制逻辑改为依赖加解密接口
- Router 不再要求启动时必须创建固定 `Cipher`
- 主密钥未就绪时服务仍能完成 HTTP 启动

### 第三阶段：开发环境配置回退（已完成）

- 在 `SecurityConfig` 增加明确的配置回退开关
- 开关启用且配置密钥有效时自动激活主密钥
- 不根据环境名称进行隐式判断

### 第四阶段：Shamir 分片恢复（已完成）

- 实现 3-of-5 分片恢复，任意 3 份且不要求输入顺序
- 校验分片批次、编号、重复项、格式和完整性
- 三份分片整批提交并原子恢复，失败时不保留部分分片
- 本阶段不提供分片生成接口和页面

分片 Token 固定使用 `EVS1.<Base64URL(JSON)>` 格式，JSON 内容包含：

- `keySetId`：本次分片生成批次的 UUID，每次重新生成必须使用新的值
- `index`：Shamir 原始分片中的唯一编号
- `data`：Base64 编码的 33 字节原始分片
- `checksum`：Token 版本和上述字段的 SHA-256 校验值

SHA-256 校验用于发现误输和数据损坏，不用于替代接口认证。本阶段一次提交正好三个 Token，不保留未达到阈值的部分分片。

### 第六阶段：系统就绪中间件（历史路径已由第 9 节替换）

- 未就绪时使用 HTTP 200 返回 `code=-2` 和 `msg=系统启动中`

- 主密钥模块的 `Ready()` 是系统就绪状态的唯一数据源

配置示例：

```yaml
security:
  ready_allowlist:
    - method: GET
      path: /api/v1/pub/health
    - method: GET
      path: /api/v1/pub/masterKey/status
    - method: POST
      path: /api/v1/pub/masterKey/shares
    - method: POST
      path: /api/v1/pub/auth/login
```

白名单在 Router 启动时完成规范化和校验，匹配规则为 HTTP Method 加精确 Path，查询参数不参与匹配。状态查询和分片提交接口是完成系统启动的必要路径，配置缺失时 Router 启动失败。Ready 中间件位于具体路由和 JWT 认证之前，未就绪的普通接口不会进入认证和业务 Handler。

## 9. 启动认证与逐份提交调整方案

> 状态：已实施
>
> 当前系统已经按本节完成受认证启动和逐份分片提交；前文公开三份整批提交仅保留为历史阶段记录

### 9.1 调整目标

- 主密钥未就绪时先完成用户认证，不再公开暴露分片输入页面和分片提交接口
- 登录后默认进入系统等待启动页面，并可切换到分片输入页面
- 分片输入页面每次只允许输入和提交一份分片
- 后端在当前实例内存中逐份累计合法分片，达到三份后恢复并激活主密钥
- 不以不同 `userId` 作为三位真实管理员的证明，也不限制同一用户提交多份不同分片
- 每次分片提交记录操作审计，但不记录分片内容、完整主密钥或可用于恢复主密钥的数据

### 9.2 认证方式

系统需要同时支持两种认证来源：

- 系统本地认证：EnvVault 提供用户名和密码登录页面及认证接口
- 公司统一认证：后续接入公司的统一身份认证

两种认证方式在认证成功后统一生成相同的用户上下文，主密钥模块只依赖统一的已认证用户信息，不感知具体认证来源。本地认证不能依赖主密钥解密能力，确保主密钥未就绪时仍可完成登录。

Ready 中间件仍位于认证中间件之前。登录接口和受保护的主密钥接口需要加入 Ready 白名单，但分片提交接口在通过 Ready 白名单后仍必须经过认证中间件。目标路由划分如下：

```text
POST /api/v1/pub/auth/login       允许未认证访问，用于系统本地登录
GET  /api/v1/masterKey/status     需要认证，允许在系统未就绪时访问
POST /api/v1/masterKey/share      需要认证，允许在系统未就绪时访问
```

公司统一认证接入后，可以增加对应的公开登录跳转和回调路径，但最终仍进入同一套主密钥接口认证链路。

当前实现允许所有已登录且未锁定用户查询启动状态并提交分片，匿名用户不能访问。后续增加角色权限时通过 `canSubmit` 和独立授权检查收紧，不改变主密钥接口契约。

### 9.3 前端流程

1. 未登录用户访问系统时进入登录页面
2. 登录成功后查询主密钥状态
3. 主密钥未就绪时进入主密钥启动页面，默认展示“系统等待启动”视图
4. 用户可以切换到“输入密钥分片”视图
5. 输入视图只提供一个密码输入框，每次提交一份 `EVS1` 分片
6. 提交成功后清空输入框并返回等待视图，重新显示当前提交进度
7. 累计达到三份后系统进入 Ready 状态，前端跳转到原目标业务页面
8. 页面提供退出登录能力，方便切换其他管理员账号，但不要求必须由不同账号提交

等待视图仅展示非敏感状态，例如 `已提交 1/3`、系统是否就绪和重新检查按钮，不展示提交人、分片编号、`keySetId` 或分片内容。

### 9.5 后端累计规则

- 分片完成格式、校验和、编号及 `keySetId` 校验后才允许进入内存
- 第一份合法分片确定当前恢复过程的 `keySetId`
- 后续分片必须具有相同 `keySetId`，不同分片编号不能重复
- 同一个 `userId` 可以提交多份不同分片，`userId` 只用于认证和操作审计
- 分片累计、重复检查和达到阈值后的激活必须在同一并发保护范围内完成
- 达到三份后立即组合并激活主密钥，成功后清除所有暂存分片字节
- 激活后拒绝继续提交分片
- 非法分片和重复分片不进入内存，也不改变已提交数量
- 单实例重启后未完成的累计状态丢失，需要重新提交，分片不写入数据库或 Redis

当前只维护一个长期有效的分片集，不提供清空当前恢复过程、切换分片集或混用多个分片集的功能。

### 9.6 操作审计与安全约束

- 记录登录结果、分片提交成功或失败、操作用户、请求 ID 和提交时间
- 审计记录只保存固定结果类型，不保存分片 Token、分片数据、`keySetId`、校验和或完整主密钥
- 日志、错误响应、链路追踪和监控标签不得包含请求体中的分片
- 登录接口和分片提交接口需要独立限流，并限制请求体大小
- 用户被锁定或认证失效时禁止查询启动详情和提交分片
- 前端分片只保存在当前输入组件的局部状态，提交结束、切换页面和组件卸载时清空引用

### 9.7 主密钥与分片集生命周期

分片“批次”在本模块中表示一次 Shamir 拆分产生的分片集，使用 `keySetId` 标识，与 Secret 历史版本的 `batchId` 无关。

需要明确区分以下操作：

| 操作 | 主密钥 | 分片集 | 已有 Secret 是否可解密 |
| --- | --- | --- | --- |
| 使用现有分片恢复系统 | 不变 | 不变 | 可以 |
| 对同一主密钥重新分片 | 不变 | 生成新的 `keySetId` 和分片 | 可以 |
| 生成全新的主密钥 | 改变 | 生成新的 `keySetId` 和分片 | 不可以，除非迁移全部密文 |

本阶段继续使用离线工具生成主密钥和唯一的 3-of-5 分片集，启动页面只负责提交既有分片，不提供生成或重新分片功能。正常运行期间不得重新执行“生成新主密钥”并直接替换当前主密钥。

如果未来需要更换主密钥，必须实现独立的主密钥轮换流程：在旧主密钥仍可用时解密全部 Secret，使用新主密钥重新加密并校验迁移结果，完成后才能停用旧主密钥和旧分片。仅对同一主密钥重新分片不会使旧分片失效，新旧分片集都可以恢复同一个主密钥。
