# 密钥搜索性能核验结果

日期：2026-10-28

本轮对象：共享密钥 Key / remark / 标签检索，以及前端搜索结果展示

## 结论

万条及十万条数据的场景可正常完成，百万条数据下的小范围或高选择性查询较快，但标签查询和大范围查询已经出现明确的性能瓶颈，不能将这次功能测试通过解释为性能目标全部达到

优先处理顺序：核对实际业务库搜索索引 → 优化标签候选及标签筛选 SQL → 优化高命中率 count / 分组分页 → 使用相同脚本复测 → 再继续搜索扩展

本轮只改动搜索核验测试及设计文档，搜索业务实现和 API 契约未调整。数据和并发测试都在专用 PostgreSQL / Redis 运行，现用本地数据库只做元数据查询

## 瓶颈证据

### 高频词：精确总数与分组分页重复处理大量命中行

百万规模高频备注词的执行计划：

- count 的 `EXPLAIN ANALYZE` 约 1,429 ms，去重后仍有 208,229 个组
- 组分页约 1,673 ms，内部排序采用 `external merge`，落盘 `85,280 kB`，约 83.3 MiB
- 即使首页只返回 20 组，计算精确总数和所有候选组的分组排序仍需要完成
- 当前页详情与标签回填约数毫秒到十余毫秒，搜索审计写入通常数毫秒，均不是这项场景的主要成本

这里的查询使用现有 folder 索引扫描大量环境行，优化器没有被强制关闭顺序扫描；不能靠强迫 GIN 或简单提高超时解决

### 标签筛选：标签已选择，但连接仍读取大量无关密钥

单标签组分页计划约 1,584 ms，`Rows Removed by Join Filter` 为 836,992；最终只剩 1,478 组
多标签 + 高频 Key 的组分页计划单独执行约 3,530 ms，正式请求还要先执行 count，因此整个请求耗尽默认 5 秒预算

后续应先评估从 `secret_tag_relation` 的有效 `tag_id → target_id` 集合出发，再利用 secret `group_id` 索引读取候选，保持租户一致性、软删除、环境和范围条件的交集
这是待对照的 SQL 优化方向，本轮没有改写生产查询

### 标签候选：返回量小，不代表 SQL 扫描量小

全范围候选总数始终只有 122 个，但百万规模执行计划中 count 约 1,257 ms、候选页约 1,243 ms，两段均关联大量环境实例
给候选增加关键词后最终只有 2 个，HTTP P95 仍约 3.72 秒，说明需要优化候选生成方式，而不是只缩小返回 pageSize

应优先评估按标签使用存在性查询、减少重复环境行参与 DISTINCT，以及复用相同范围的候选集合；不能缓存明文值，也不能在未来权限变化时复用越权候选

## 并发与资源

每级预热 30 秒，再测量 180 秒，等待在途请求完成。请求比例为：稀有 Key 40%、项目范围 20%、单标签 10%、标签候选 10%、高频备注 10%、全范围浏览 10%
这是闭环 HTTP 负载，每个 worker 完成一次请求后才发下一次，吞吐量表示这个负载下的实测完成速率

| 并发 | 请求数 | 成功 | 查询超时 | 完整 HTTP P95 | 实测请求 / 秒，含失败 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 157 | 157 | 0 | 3,116.6 ms | 0.86 |
| 5 | 480 | 400 | 80 | 5,017.8 ms | 2.66 |
| 10 / 20 | 未执行 | — | — | — | 按方案在并发 5 出现错误后停止升压 |

并发 5 的失败率为 16.7%，成功吞吐约 2.21 次 / 秒。失败按场景分布为：高频备注 25 / 45、单标签 5 / 50、标签候选 50 / 50
同一级中，稀有 Key 190 / 190 成功，P95 20.6 ms；项目范围 100 / 100 成功，P95 158.7 ms
因此这是当前数据与负载组合下的瓶颈，不能理解成系统的所有查询都只支持并发 1，或简单地把全系统容量定为 5

两级连接池 `WaitCount=0`、`WaitDuration=0`，未发现应用池排队。数据库 CPU 采样峰值约 428.5%，已接近 4 CPU 配额；短时采样可能略超过名义配额
全部采样阶段 PostgreSQL 内存峰值约 892.7 MiB，Redis 保持约 10 MiB；累计容器块 I/O 约读 430 MB / 写 22.9 GB，包含造数、索引及临时排序
Go RSS 峰值约 191.3 MiB，包含测试数据期望值计算；并发 5 测量结束时 Go heap 约 4.6 MiB，不能拿测试进程峰值直接作为生产实例的内存需求

主动取消检查：客户端在 50 ms 后取消全范围重查询，随即查询 `pg_stat_activity` 未发现其他活跃查询；随后 3 次稀有 Key 请求全部成功，P95 10.4 ms
该检查说明当前取消路径能结束查询并复用连接，不替代长期取消风暴或线上网络断连测试

查询预算只覆盖数据库与解密，所以部分超时响应的完整 HTTP 耗时大于 5 秒；本轮 P99 最高约 5.24 秒，报告没有把 5 秒当作 HTTP 的绝对上限

### 浏览器

使用当前 `env-vault-web` 构建产物，Chrome 无头模式、1600 × 1000 视口，经上述本地 Nginx 调用真实测试后端，不使用搜索结果 Mock

- 搜索页进入、Ready / auth/me / 层级查询正常，最终一轮页面 JavaScript 错误为 0
- 稀有 Key 展示 1 组、4 个环境，点击到显示约 109 ms；后续重复约 81 ms
- 中文备注展示 20 组、80 个环境，点击到显示约 127 ms
- 翻到第二页确实发出 `pageNum=2`，仍是 20 组、总数 2,497，接口完成约 92 ms
- 切到 UI 最大 100 组 / 页，实际渲染 400 条环境行，点击到行节点出现约 524 ms
- 发起高频词搜索后修改关键词，浏览器确认旧请求取消，新稀有词结果正常展示
- 标签候选第一页和“加载更多”第二页均实际调用后端，第二页返回 50 个、总数 122
- 通过范围选择器实际选择项目，再勾选 dev / test，确认请求只包含这个项目与两个环境，返回 20 组、总数 31,218，每组只有 dev / test 值

上述浏览器时间是单次交互观测，包含自动化点击、网络与表格更新，不作为线上 P95，也不等于独立 FCP / LCP 测量

## 与验收目标的对照

本轮已确认百万规模的标签候选不满足 P95 500 ms 目标，高频备注词也未稳定满足低并发 P95 3 秒目标，组合标签查询存在超时
成功结果的分页 / 环境正确性检查通过；超时作为标准业务错误返回，不把错误响应伪装成空页成功

## 复现、证据和边界

执行方法见 [核验方案](secret-search-performance.md) 的“本轮可复用的执行入口”

本机原始证据位于 `.local/search-performance/20261028/`：

- `local-database-metadata.json`：现用本地数据库只读元数据

- `large/http-results.json`、`http-large.log`：长值专项及增加范围 / 标签身份断言后的快速回归

限制：

- 这是本机单服务实例的闭环并发测试，实际负载分布、网络、磁盘和多实例能力需要部署环境复测

- PostgreSQL 资源来自全部采样阶段，包含造数和建索引，不把峰值当成纯查询稳态
- 资源权限过滤仍是预留点，本轮不宣称已经验证资源 / 环境权限隔离
- 未访问公司真实登录、Ingress / Higress 或集群数据，不据本机结果承诺线上容量
- 本轮只测 Key、备注和标签，值检索、统计聚合、游标分页、导出均未增加

后续先针对这里的 SQL 瓶颈做独立优化和同条件对照，保留组级分页、返回结构、字面量包含匹配及未来权限过滤入口
